# 评论投递采用同幂等键有限次重试

一次评论可能触发远端智能体执行，而网络超时或 `5xx` 不能证明服务端未落库，无约束重发会造成重复发言或重复触发 Run。插件为单次评论发送（含 AskUser 卡片回答）固定连接、目标讨论、正文、附件 ID 全集与 `Idempotency-Key`（连接、Issue、讨论、`clientMessageId` 及显式回复目标的 JSON 的 SHA-256，非随机值；最长 255 字节）。因 Multica 服务端幂等指纹不含正文和附件 ID，同 key 重试严禁改动正文、目标或附件；仅在当次请求遇到网络错误或 `5xx` 时最多自动尝试 3 次。

附件逐件上传且每件只尝试一次（上传无幂等），任一上传失败、空或非法 ID 都不提交评论，并提示可能留下孤立附件。评论重试复用全部已上传 ID，不重传文件；附件输入在进程内保留指纹及首次结果，重复派发不重新上传，变更输入拒绝。上传单独放宽至 120 秒，其余请求保持 10 秒，每次远端操作检查当前身份。

三次尝试仍失败或收到确定性拒绝时，保留已乐观展示的原生用户输入并追加一条错误提示（AskUser 原生表单保留以便重填提交），由用户在确认远端状态后决定是否重发；插件不跨进程重启持久化失败草稿或未决投递。成功发送持久化 `clientMessageId → commentId / rootId` 用于同步回声去重，附件发送另存成功原文、指纹与展示元数据。提交成功而映射未落盘时崩溃仍可能失去对账关系，与纯文本边界相同；不自动续传或跨重启重发。评论已保存与远端 Run 是否启动始终分别判断与展示。

## 考虑过的替代方案

- **无 `Idempotency-Key` 直接重试或允许修改重试正文**：网络丢包重放会产生重复评论，修改正文复用旧 key 则会被服务端幂等回执静默吞掉新内容。
- **持久化投递状态机、7 天 `GET .../comments/idempotent` 回执核实与 Stop epoch 栅栏**：首版曾实现跨重启待核实队列与管理页核实/重发入口，但引入了沉重的持久状态与界面负担，且仍无法消除超期或不支持幂等回执实例上的不确定性，现已精简移除。
