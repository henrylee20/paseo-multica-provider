# 评论投递采用同幂等键有限次重试

一次评论可能触发远端智能体执行，而网络超时或 `5xx` 不能证明服务端未落库，无约束重发会造成重复发言或重复触发 Run。插件为单次评论发送（含 AskUser 卡片回答）固定连接、目标讨论、正文与随机 `Idempotency-Key`（最长 255 字节，因 Multica 服务端幂等指纹不含评论正文，同 key 重试严禁改动正文或目标），仅在当次请求遇到网络错误或 `5xx` 时最多自动尝试 3 次。

三次尝试仍失败或收到确定性拒绝时，保留已乐观展示的原生用户输入并追加一条错误提示（AskUser 原生表单保留以便重填提交），由用户在确认远端状态后决定是否重发；插件不跨进程重启持久化失败草稿，成功发送只持久化 `clientMessageId → commentId / rootId` 用于同步回声去重。评论已保存与远端 Run 是否启动始终分别判断与展示。

## 考虑过的替代方案

- **无 `Idempotency-Key` 直接重试或允许修改重试正文**：网络丢包重放会产生重复评论，修改正文复用旧 key 则会被服务端幂等回执静默吞掉新内容。
- **持久化投递状态机、7 天 `GET .../comments/idempotent` 回执核实与 Stop epoch 栅栏**：首版曾实现跨重启待核实队列与管理页核实/重发入口，但引入了沉重的持久状态与界面负担，且仍无法消除超期或不支持幂等回执实例上的不确定性，现已精简移除。
