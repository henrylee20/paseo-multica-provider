# 仅在具备去重保证时自动重试评论

一次评论可能触发远端执行，网络超时又不能证明评论未保存，因此盲目重试会重复发言或执行。
同一次投递使用稳定请求编号与不变的正文和目标，先查询回执；仅在已验证服务提供去重保证且仍在有效期内自动重试。
超过保证期限、服务不支持或结果仍无法确认时保留待核实状态，由用户核实后决定是否重发；评论保存回执不等于执行触发或进程结束的确认。

#10 的投递记录先于宿主 admission 保存不变输入、连接和目标、时间、停止 epoch、clientMessageId 与随机 UUID key。普通首次 POST 即带 Idempotency-Key，但这本身不是服务已支持去重的证据；本切片不自动重试。HTTP 5xx、超时、断线及无法校验的成功回执都保留 pending_verification，确定拒绝和发出请求前的失败保存 failed。收到的评论 ID、作者、父目标、来源时间与可选 trigger_outcomes 单独保存；trigger_outcomes 也不替代真实 Run 状态。

原生 `prompt.steer` 的承诺是已接收输入，远端结果由独立插件行报告。实际 0.15.3 会将 failed 或错误 turn ID 转为 interrupt 后替换，因此在任何 await 前缓存当前聚合 turn UUID，并在持久接收后返回这个 ID，即使该周期已结束或后续周期开始。每轮 turn ID 仍唯一，不复用已完成 ID。若插件存储故障导致输入根本未能持久接收，运行中只用匹配 ID 阻止意外取消，明确追加原生未接收错误且不发 HTTP；不能声称已持久保存或已发表。全局存储故障可能连宿主错误记录也无法落盘，界面不作持久保证。

停止 epoch 在首次 POST 领取前使用原值校验，不为旧记录刷新 epoch。进程重启后未确认记录只恢复本地输入／状态展示，不重复 POST；未来 #11 的回执恢复与重试必须沿用这份不变记录和 StopCoordinator.guardDelivery，并先验证服务真实去重能力及期限。
