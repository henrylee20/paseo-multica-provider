# Paseo–Multica 实现计划

这是已获整体确认的 [首版规格](./spec.md) 的工程实现建议；已通过 `/to-spec` 发布 [规格 issue #1](https://github.com/henrylee20/paseo-multica-provider/issues/1)，未开始编码。
产品行为以规格和已确认 ADR 为准。模块名称与存储实现可调整，不能借工程调整改变角色映射、隐藏、停止或重试语义。

## 模块职责

| 模块 | 责任与边界 |
| --- | --- |
| CLI 登录适配器 | 只读解析默认或命名 profile、配置根目录、有效服务地址与凭据；遵循环境覆盖和任务隔离，检测登录变更，不向客户端暴露凭据 |
| Multica 客户端 | 身份、工作区、筛选元数据、Issue/评论/Run 读取，评论投递、回执、取消和工作区实时事件；区分 HTTP 成功与实际业务结果 |
| 本地状态存储 | 连接身份、远端到 Paseo 的映射、首次 Run 归属、人工隐藏、快照与游标、投递记录、取消失败；原子保存关键关联 |
| 任务同步器 | 根据快照与事件重算筛选范围，维护原生层级，恢复和归档对象；独立于某个打开的 tab |
| Paseo 适配层 | 封装所需的宿主接口、占位目录、创建与恢复操作；明确高层 API 和低层 SDK 的区别 |
| Provider 会话 | 评论与原生消息投影、历史回放、输入与活动 turn、中断和资源关闭；不创建本地 LLM 执行 |
| 客户端贡献 | 幂等引导 RPC、管理页、Run 执行段 renderer、明细按需读取、问题与恢复入口 |

采用与 Paseo 插件生态一致的 TypeScript 接口。具体存储依赖与打包方式以宿主兼容性验证为准，不把尚未验证的依赖写成既定要求。

## 身份与持久化

- 连接身份包含 CLI 解析出的 API 服务地址和用户身份，Token 轮换不改变身份；凭据只在 daemon 内存中使用，仍由 CLI 存储，不额外写入插件状态、源码或客户端静态包。
- 本地映射引用不可变的远端 ID，不按标题、显示名称或路径猜测业务身份。
- 分别保存工作区到 project、Issue 到 workspace、根评论到 agent、Run 到首次展示归属的关联；主讨论使用独立的本地标识。
- 每项任务保留独立的目录关联，避免多个无关任务共用同一 cwd 的 Paseo 状态分组；目录不放置实际远端代码，也不在自动归档时删除。
- 人工隐藏与自动退出筛选是不同原因。记录同步器自身发起的生命周期操作，避免把自动归档误标为人工隐藏。
- 原子保存投递身份与不可变正文、目标、原始请求时间和回执；不能在重试时悄悄更改同一请求编号的正文。

## CLI 鉴权接入

以已安装 Multica CLI 0.6.3（`18fa9f728a9e25f2465df2789631edb2a75442ad`）为已核查基线，使用版本可识别的只读配置适配器；其 Go loader 位于 internal 包，没有可直接依赖的跨项目公开鉴权 SDK。

- 默认配置为运行用户的 `~/.multica/config.json`，命名 profile 为 `~/.multica/profiles/<name>/config.json`；`MULTICA_TASK_CONFIG_ROOT` 会改变配置根目录，不能绕开隔离去读取拥有者的全局凭据。
- 默认 profile 为空；不存在已核查 CLI 支持的全局 active-profile 或 `MULTICA_PROFILE` 解析器。插件 profile 选项等价于 CLI 的 `--profile`，不根据目录修改时间猜测用户意图。
- CLI API 地址优先级是命令行 `--server-url`、环境 `MULTICA_SERVER_URL`、profile 的 `server_url`。插件默认不额外覆盖服务地址，采用 CLI 环境与所选 profile 的有效值，按 CLI 规则规范化 URL。
- 凭据优先使用非空 `MULTICA_TOKEN`，否则使用所选 profile 的 token；daemon 任务上下文的特殊隔离检查必须保持。API 地址与凭据作为一次解析的上下文使用，不能将独立改动的插件 URL 与旧凭据拼接。
- 将 CLI 凭据作为不透明值使用，不靠 token 前缀猜测身份或强制认定登录类型；实际用户身份由对应服务验证。
- `app_url` 用于前端链接，不能代替 API base。自部署主机、端口和 CLI 支持的 URL 形式需要配置夹具验证，不硬编码云服务域名。
- 配置可能通过原子文件替换更新。采用可恢复的监测与定期重读，不仅监听旧文件 inode；鉴权失败时重新检查有效上下文，身份变化先完成映射隔离再恢复写入。
- CLI 没有 token 导出命令，`config show` 不输出凭据，`auth status` 会输出 token 前缀。不能通过这类状态命令抓取或记录凭据；日志和 RPC 只返回非敏感连接状态。
- 配置缺失、权限不足、JSON 损坏、未登录和凭据失效应区分提示。不能静默回退云服务、继续使用已移除凭据或代替用户执行登录/登出。

新增验证使用临时目录与虚构凭据：默认/命名 profile、自部署地址、API 与前端地址不同、环境覆盖、任务隔离、同身份凭据轮换、服务/账号切换、原子替换、登出及过期。不依赖或输出用户真实凭据。

## 生命周期与同步

1. 客户端贡献加载后通过幂等 RPC 引导服务端同步；连接存续期间提供重试引导，不能只依赖不会每次重连重跑的 setup。
2. 服务端读取 CLI 有效登录上下文并获取连接身份，校验配置，加载持久映射，然后按工作区抓取分页快照并订阅实时事件。
3. 同一连接只启动一个同步循环；多人或多个客户端连接不重复启动任务或映射。
4. 根据整个已启用工作区的事件检查任务是否进入规则，不能只监听已收录任务。
5. 对匹配任务维护 project/workspace/tab；读取 Thread、Run 概要。首次 Run 归属判定前补齐必要关联信息，已固定归属不重算。
6. 规则退出使用 workspace 级归档路径，单纯关闭会话只释放资源。恢复先恢复 workspace，再恢复需要的 agent，并尊重人工隐藏。
7. 不使用 `refreshAgent` 对运行中 agent 做周期同步；不把活动 handle 的 import 当作 upsert，也不以重新 resume 创建新身份。
8. 重连后重新核对快照和筛选范围。运行消息按 `seq` 补读；没有全局事件游标重放保证时，不能仅凭 WebSocket 重新连上就认定数据完整。

## 评论投递

- 普通 Thread 输入固定根评论为 parent；主讨论输入无 parent，创建真实根评论。当前输入只处理文本。
- 校验会话是否绑定已映射的 Multica 任务；缺少任务上下文时提供配置引导，不从任意本地目录意外创建远端 Issue。
- 同一次投递关联 `clientMessageId`、稳定幂等键及返回的 comment ID，用于重复请求、进程恢复和原生回显协调。
- 验证实际服务的幂等能力后，在有效期内优先查回执，再以原 key 重试。接口不支持、保证期已过、原评论删除冲突或无法确定结果时停止自动重试，保留待核实状态。
- 源码中的 7 天保留期、255 长度上限和不包含正文的服务端指纹都是边界条件，不能忽略；目标服务能力仍须验证。
- 评论保存与触发结果分别处理；回执不用于推断某个 agent 必然开始执行。

### Paseo steer 的专门验证

外部插件必须声明 `prompt.steer`，并对 `delivery: steer` 返回匹配当前 Paseo turn 的结果。
已核查的宿主会将 failed 或不匹配结果视为 unavailable，再走中断替换。因此普通网络失败不能简单映射为 steer unavailable，否则可能意外取消正在运行的 Multica Run。

候选实现是先可靠接收并记录投递意图，再把实际远端投递结果作为独立状态呈现，始终区分“插件已接收”与“评论已发表”。这需要针对真实适配器验证，包括 HTTP 失败、响应丢失、活动 turn 恰好结束和重复投递；它目前是工程方案，不能当作已经验证的接口能力。
同时验证停止与自动重试的竞态，避免停止之后因旧的待投递输入意外重新触发执行；不得静默丢弃输入或声称未发表的评论已发表。

## 时间线与活动状态

- 原始评论使用原生 user/assistant 消息；系统事件、更正和删除提示作为独立记录，不用重复 assistant 回复代替。
- 姓名用于展示，用户 ID 和作者类型用于角色判断。一次原生发送与服务端回显只生成一条实际评论投影。
- 每个远端 Run 使用稳定的插件执行段 ID。单行只放摘要与必要状态，详细输出通过 RPC 按需读取，避免超过 64 KiB 插件行限制。
- 一个 tab 只对应一个活动 Paseo turn 槽位；聚合该 tab 多个远端 Run 的状态，远端 Run ID 不直接充当多个并行原生 turn。
- 运行输出有稳定 call ID 时关联工具输入、输出；旧数据缺字段或输出被截断时明确保留缺失状态，不猜造完整内容。
- 首次回放、重复事件、补历史、评论更正和 Run 更新必须有可复现的去重规则；同步器和会话不能各自重复投影同一条内容。

## 停止与恢复

- 接收停止时固定本次操作的未结束 Run 集合，按单 Run 接口取消；不用 agent 级全部取消接口扩大范围。
- 已终态的 Run 按返回事实处理，不能把 HTTP 200 一律标成“已取消”。
- 集合之外随后产生的 Run 不冒充本次取消成功；多个 Run 的成功、失败与最新状态逐项保存。
- 完整成功与部分失败的响应必须符合 Paseo 的真实取消状态，不能应答虚假的停止成功来强制结算。
- 关闭 tab 即使继续归档，失败信息仍独立存在于管理页；重试不会自动取消人工隐藏。
- 区分取消状态与进程清理确认；对网络中断展示最后确认状态及同步状态。

## 实施顺序

1. **宿主与连接契约验证**：先验证 CLI 登录适配器与自部署地址；再验证最小插件加载、provider 会话、RPC 引导、renderer、目录与身份创建/恢复，确认当前运行宿主版本并探测实际 Multica 能力。
2. **状态与只读同步**：持久身份、筛选、原生层级、人工隐藏、概要与历史读取、唯一 Run 归属。
3. **会话投影**：原生消息、作者、回显去重、执行段、评论更正与系统事件；验证重连重建。
4. **写入与停止**：普通评论、新 Thread、幂等回执、可靠重试、原生停止、部分失败与竞态。
5. **管理与验收**：配置、隐藏/历史恢复、问题处理和目标宿主实测，完成安装及使用说明。

## 验证要求

行为测试覆盖 [已确认验收场景](./design.md#已确认决策的验收场景尚未执行)，重点使用多 Thread、多 agent、多 Run、断线重连、重复事件和响应丢失的组合。
适配器契约检查应覆盖真实 Paseo 消息边界，避免只测试自己的映射函数；HTTP/WebSocket 模拟验证服务错误与补读，目标实例验收验证权限、版本和完整使用流程。

规格中的运行验收尚未执行。实现遇到无法在已选范围内满足的宿主限制时，记录具体证据和受影响行为，再调整设计；不能把静态核查、候选方案或模拟结果报告为真实服务已经可用。
