# askuser 后台主动加载（#24）

后台完成 Thread 卡片与 Run 概要同步后，只为包含当前连接用户可答、未决、未本地收起且已核对完整 timeline 的卡片调用原生 `listCommands(agentId)`。所属 Multica 任务必须仍在启用的规则范围内；人工隐藏、自动归档、失权、归档处理中与讨论生命周期 hold 均阻止加载。原生 agent 与活跃 Paseo 工作区的身份也会重新核对。

此调用使用 SDK 的交互加载路径，未传 `purpose: "history"`。已加载且没有延迟首次权限的 provider 讨论通过生命周期订阅识别并跳过；初次 import 已打开会话但仍有延迟新权限时，也等待一次无中断的 `listCommands` 作为原生注册完成的确认。未加载但包含远端活动 Run 的讨论仍可恢复问题。加载不调用 `refreshAgent`、不发送中断、不取消远端 Run，也不人为结束或替换聚合 turn。

同一连接／任务／Thread 的后台加载同时去重，尝试之间至少间隔 60 秒，失败同样限流。单个原生请求失败不会阻断其他 Thread 或任务的同步。明确点击「重新展开作答」后，RPC 重新核对卡片与身份；若原生宿主已释放空闲会话，则立即加载，保留隐藏、归档、权限与 hold 检查，不受后台重试间隔限制。

原生隐藏恢复和后台同步共用串行宿主操作队列，恢复持有 hold 时不会并行开始后台加载；provider 打开与提问 RPC 同时保留 hold 检查。模拟贡献边界测试暂停原生恢复，观察 `session.open` 被拒绝、提问重展被拒绝且没有新增 `listCommands` 或原生权限。

## 原生回放与注意力边界

固定核查的 Paseo 0.17.4 源码在初次打开期间，将 `session.permission` 作为非 live 历史恢复；仅发出 `session.ready` 还不能证明原生 manager 已完成注册。插件用仅在当前进程内保存的首次发现标记区分新卡片和持久缓存历史：缓存旧权限仍在 ready 前回放，首次发现且在打开期间遇到的权限则延迟发出，直到 `await listCommands(agentId)` 返回后明确公布。即使 import 已打开 provider 会话，也保留这道确认；ready 后的其他状态更新不能提前释放延迟权限。已经完成加载的运行中会话收到新卡片时直接发出 live 权限，不额外调用加载或中断。

首次发现标记只在真正发出权限后消除，不写入持久状态。重复同步不会重复公布；后续 provider 连接或 daemon 重启按缓存历史恢复，不重复制造首次发现注意力。新权限仍包含可读的卡片 title 与 description。宿主注意力策略决定最终是否通知，焦点、在线客户端和推送配置均会影响结果；操作系统通知标题固定，卡片标题／说明进入通知正文。

`tests/askuser-wakeup.test.ts` 通过公开贡献／RPC／provider 边界和模拟原生宿主验证加载、权限事件、状态保护、限流、失败隔离及 Run 不受中断。测试在 provider ready 后暂停原生注册，确认首次未打开发现和自动 import 的新权限均等待原生完成；另覆盖期间其他卡片更新、已运行会话直接 live、重启及新连接缓存 pre-ready 回放。`needs_input` 由宿主根据待决权限推导；这些自动化测试没有运行真实侧栏、QuestionFormCard、注意力广播或操作系统通知。

本轮没有安装、reload 插件，没有连接真实 daemon，也没有读取或写入真实 Multica 服务。真实原生视觉与通知验收保留给 #26 的手动清单；模拟结果不能替代这些验收。
